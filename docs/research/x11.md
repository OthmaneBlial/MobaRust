# X11 forwarding and display-server strategy

## Status

The native SSH transport has an opt-in external-display forwarding path. It
does not bundle an X server, discover a user's display environment, or claim
MobaXterm-equivalent integrated X11 support. The cross-platform server and
packaging matrix remains open.

This document separates three capabilities that are often incorrectly treated
as one feature:

1. **SSH X11 forwarding** — requests an `x11-req` channel and carries remote
   X11 traffic through an authenticated SSH connection.
2. **An integrated X server** — accepts X11 client connections locally and
   renders them in the desktop environment.
3. **External X-server integration** — forwards to an X server already
   installed and explicitly selected by the operator.

SSH forwarding alone is not an X server. A remote application can only render
when a compatible local display endpoint is available.

## Current architecture

The shipped native path is deliberately explicit:

```text
React opt-in setting
  -> typed SSH request with explicit display target
  -> Rust validates loopback TCP or absolute Unix target
  -> Rust sends SSH x11-req and creates the temporary cookie
  -> SSH server opens an X11 channel
  -> Rust bridges that channel to the selected local display
  -> external X server renders the remote client
```

The display target is not read from `DISPLAY`, `$DISPLAY`, `.Xauthority`, or
any other ambient configuration. Accepted targets are loopback TCP sockets or
explicit absolute Unix-socket paths. The cookie remains native, channels are
bounded to eight simultaneous display channels, and cancellation is owned by
the Rust connection lifecycle.

The React layer receives status only. It never receives the X11 byte stream,
the forwarding cookie, or a local display credential.

## Architecture options

| Option | Benefits | Costs and risks | Decision |
| --- | --- | --- | --- |
| SSH forwarding to an external server | Small application footprint; clear ownership; works with existing operator tooling | Requires a separately installed and configured X server; platform UX varies | Current path |
| Bundled/integrated X-server helper | MobaXterm-like first-run experience; one product surface | Large native dependency, display/window integration, security boundary, license review, updates, and packaging burden | Defer pending dedicated feasibility study |
| External-server discovery and auto-start | Convenient when a known server is installed | Reads ambient state, may launch software or change firewall behavior unexpectedly, and creates version-specific assumptions | Reject automatic behavior; consider explicit user-selected integration later |
| Wayland-native or browser rendering replacement | Better fit for some modern Linux desktops | Not an X11 server; compatibility and protocol semantics differ | Not a substitute for X11 support |

The current decision is the smallest real capability with a controlled trust
boundary: provide excellent explicit external-server integration and keep an
integrated server as a separate project.

## Platform behavior

### Windows

MobaRust should not assume that an X server is present on Windows. An operator
may use an approved external X server or a WSL/WSLg setup, but the application
must not install one, start one implicitly, edit firewall rules, or infer a
display from unrelated environment variables. The UI should explain that
forwarding is available only after the selected external display endpoint is
running and reachable on the explicitly configured loopback target.

The Windows matrix still needs real checks for:

- external-server startup and shutdown ownership;
- loopback firewall prompts and failure messages;
- keyboard layout and IME behavior;
- high-DPI and multi-monitor rendering;
- WSL/WSLg interoperability where that is an approved supported path;
- clean packaging without a bundled X-server license or runtime dependency.

### Linux

Linux installations may expose X11 directly, Xwayland, or a compositor-specific
display path. MobaRust must not assume that an X11 display is available merely
because the desktop is graphical. The operator must select an explicit local
TCP or Unix target, and the UI must distinguish a missing external server from
an SSH forwarding failure.

The matrix needs checks on at least one X11 session and one Wayland session,
including Unix-socket permissions, loopback TCP behavior, clipboard semantics,
scaling, and cancellation. No distribution-specific package manager action is
part of normal setup.

### macOS

macOS does not provide a bundled MobaRust X server in this project. An
operator-installed external X server is a separate prerequisite. MobaRust must
not install it, read its authorization files, or silently choose a display.
Explicit loopback TCP forwarding is the portable initial path; Unix-socket
behavior requires a separately verified server and filesystem-permission test.

The matrix needs checks for Retina scaling, native keyboard shortcuts, external
server lifecycle, clipboard boundaries, and an absent-server diagnostic. The
repository test may use a pre-existing Xvfb binary as a disposable local
fixture when the system Unix-socket directory already exists; it does not
install or configure an external X server, opens no TCP listener, and does not
claim macOS external-server interoperability.

## Security implications

- X11 forwarding is opt-in and remote traffic is carried inside the SSH
  transport, but the selected local display remains a powerful local trust
  boundary.
- An X11 client may be able to observe or interact with other clients on the
  same display. The UI must warn users before enabling forwarding to a shared
  display.
- The temporary `MIT-MAGIC-COOKIE-1` value must be generated, used, and
  discarded in native code. It must not be serialized, logged, exported, or
  placed in the frontend state.
- Non-loopback display targets are rejected by default to avoid turning an SSH
  session into an unexpected network bridge. Any future exception requires a
  separate threat model and an explicit approval flow.
- Remote X11 payloads are untrusted bytes. They must never be rendered as web
  content or interpreted as frontend commands.
- Disconnection, timeout, and cancellation must close the SSH channel and the
  local display socket without leaving a child server, cookie, or temporary
  authorization file behind.

X11 forwarding does not protect the local machine from a malicious remote
X11 client, a malicious local process, a compromised external X server, or
an operator who explicitly shares the display. These limits belong in the
security help text and release documentation.

## Dependencies and packaging

The current external-server path uses the SSH implementation and standard
socket primitives already present in MobaRust. It introduces no X-server
binary, no global package installation, and no platform-specific server asset.

An integrated server would require a new native helper boundary and a separate
review of:

- protocol and codec maintenance;
- window-system and compositor integration;
- clipboard and input permissions;
- crash containment and cancellation;
- Windows, Linux, and macOS packaging;
- third-party licenses and notices;
- update and vulnerability handling;
- clean-install and signed-distribution evidence.

The integrated option must not be enabled by copying code or assets from
reference applications with incompatible licenses. External integration is
the initial legal and operationally smaller path, not proof that an integrated
server is feasible.

## Verification status and acceptance gates

Already verified locally:

- strict parsing rejects `:0`, `$DISPLAY`, host discovery, and non-loopback
  TCP targets;
- the native path requires an explicit display target;
- a disposable SSH fixture forwards a synthetic X11 payload to a loopback
  display fixture;
- disabled X11 channels are rejected and the bridge is bounded and
  cancellable;
- no personal `DISPLAY`, `.Xauthority`, SSH key, agent, Keychain entry, or
  remote host is used by the test suite.

The optional Xvfb integration path is implemented with `-nolisten tcp` and a
system Unix socket, but it was skipped on the current macOS host because
`/tmp/.X11-unix` is absent and cannot be safely created by a non-root test.
That path needs a dedicated Linux/X11 runtime or an equivalent system fixture
before it can be recorded as local interoperability evidence.

Still required before claiming cross-platform X11 support:

- Windows external-server interoperability evidence;
- Linux X11 and Wayland interoperability evidence;
- macOS external-server interoperability evidence;
- clipboard, scaling, keyboard, multi-monitor, and failure behavior per
  supported platform;
- documented external-server setup and removal behavior;
- decision on whether an integrated server is worth its security, license,
  and packaging cost.

Until those gates are met, the honest product wording is **SSH X11 forwarding
to an explicitly configured external display**, not **integrated X11 server**.
